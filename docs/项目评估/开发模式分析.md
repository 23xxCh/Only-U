# Only-U 项目开发模式评估（软件工程视角）

> 评估日期：2026-08-22
> 评估对象：`23xxCh/Only-U`（赤兔 AI 黑客松，产品赛道「单人成军」，一天半开发 + 半天评奖）
> 评估方法：基于仓库文档、分支与提交历史的静态分析（只读，未修改任何文件）

## 结论先行

本项目采用的是一套 **「规范基线 + 票驱动的多智能体协作开发」（spec-driven, ticket-dispatched multi-agent development）** 模式。它不是传统的 Scrum/瀑布，而是把以下工程实践拼在一起：

```
文档权威链（CONTEXT → plan → designs → ADR）→ Issue 分诊看板 → AFK agent 实现 → 分支 + PR 集成 → TDD 保障 → 演示驱动验收
```

---

## 1. 规范先行（Plan / Spec-Driven）——需求在前、实现靠后

仓库建立了一条严格的「文档权威链」，且明确规定优先级（[../README.md](../README.md)）：

```
CONTEXT.md（领域术语）→ plan.md（开发基线）→ designs/（已批准设计）→ ADR（已拍板决策）→ agents/（协作约定）
```

关键特征：显式声明「**哪些文档不是实现依据**」——队友写的大 PRD、长需求文档被降级为「需求证据」，冲突时以 [plan.md](../plan.md) + ADR-0002 + ADR-0005 为准。这是一种**单一事实来源（single source of truth）+ 版本化规格**的做法，防止文档漂移导致实现返工。

## 2. ADR 决策治理（Architecture Decision Records）

[adr/](../adr/) 目录里有 5 条编号 ADR，每条带 `Status: accepted`，记录「为什么这么拍板」：

- ADR-0001：只做软件 U 盘包，不做硬件
- ADR-0002：锁定黑客松范围（对抗 PRD 漂移）
- ADR-0003：有网 Agent 壳定为 dsh-TUI 插件
- ADR-0004：开发基座 dsh-TUI 源码快照提案
- ADR-0005：U 盘密封运行时（FAT32 装不下 pnpm 符号链接 → 扁平 CLI + 便携 Node）

这是 ThoughtWorks 提出的 ADR 实践，在黑客松场景里被用来**锁死范围、防止口头决策丢失**。

## 3. 票驱动 + 三态分诊（Issue-driven + triage）

真正的交接物不是聊天记录，而是 GitHub Issue（[../发给合作者-如何让他们的agent干活.md](../发给合作者-如何让他们的agent干活.md) 第 7 节明确「不要转发聊天记录」）。每张票经过固定流水线：

```
/grill-with-docs（对齐术语）→ /to-prd（需求成文）→ /to-issues（拆垂直切片）→ /triage（打标签）→ 认领 → feat/N-xxx 分支 → PR（Closes #N）
```

五类 triage 标签（`needs-triage` / `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`）扮演**看板**角色，其中 `ready-for-agent` 是「规格完备、可以交给 AI agent 全自动做」的门禁（[agents/triage-labels.md](../agents/triage-labels.md)）。

`ready-for-agent` 的票必须同时满足：

- 有「做什么」和验收标准
- 依赖写清（Blocked by #几，或写 None）
- 不需要现场插 U 盘、产品拍板、账号权限等只有人能做的事

## 4. 人机分工明确（Human + AI Agent 混编团队）

[plan.md](../plan.md) 第 5 节的切片表里每项都标注 **AFK（away-from-keyboard，agent 全自动）** 或 **HITL（human-in-the-loop，人盯）**。角色分工：

- **队长**：需求调研 + 架构（写 plan / ADR / Issue 正文）
- **两个合作者**：只写代码、开 PR——但实际实现也交给各自的 agent（Grok / Claude Code / Codex），人负责贴「开工提示词」和 review PR

这是典型的 **agentic software engineering** 组织方式：人类承担产品决策和验收，agent 承担实现。

## 5. 轻量分支工作流（GitHub Flow 变体）

[../发给合作者-如何让他们的agent干活.md](../发给合作者-如何让他们的agent干活.md) 第 4 节：

- main 受保护（约定），不直接推
- 一张票一条 `feat/N-短名` 分支，一个 PR，`Closes #N` 自动关票
- 每天开工先 pull origin main
- 禁 `push --force`
- 分支前缀规约：`feat/` `fix/` `docs/` `chore/`，带 Issue 号（如 `feat/2-diagnose-scan-cap`）

## 6. 票内强制 TDD

开工提示词第 7 步要求「走 /tdd：先写失败测试，再写最小实现，再重构」，且已落地 [../../portable/tests/diagnose.Tests.ps1](../../portable/tests/diagnose.Tests.ps1)（PowerShell 侧的 Pester 风格测试）。

## 7. DDD 轻量化（Ubiquitous Language）

根目录 [CONTEXT.md](../../CONTEXT.md) 用「术语 + Avoid 同义词 + 关系 + 示例对话 + 歧义记录」的方式固化领域语言（如「烘焙」「运维会话」「误删防护」），并要求所有人/agent 不得自造同义词。这是领域驱动设计里「通用语言」实践的裁剪版，用来对齐三个 agent 的上下文。

## 8. 时间盒 + 演示驱动 + 风险降级路径

- 1.5 天黑客松本身是极端时间盒
- [plan.md](../plan.md) 第 3 节以「评委 3 分钟演示」作为 Definition of Done
- 第 7 节预设**保底方案**：TUI 起不来就退化为纯脚本演示（「Agent 层用同一套脚本」的话术）
- 第 8 节的「砍掉的东西」表是轻量级**范围管理**，防止冲刺中返工

---

## 总结

这是一个**为黑客松定制的「规范驱动开发（Spec-Driven Development）+ ADR 治理 + Issue 分诊看板 + 多智能体（人机混编）并行实现」模型**：

| 维度 | 做法 |
|---|---|
| 上下文一致 | 文档权威链 + CONTEXT.md 术语表 |
| 决策一致 | ADR 编号存档，拍板即锁定 |
| 任务分派 | GitHub Issue + 五类 triage 标签 |
| 并行实现 | 一人一分支，AFK agent 按票实现 |
| 质量底线 | 票内 TDD + PR review + 人盯演示 |
| 时间盒保障 | 演示驱动 + 降级路径 + 范围锁死 |

它借鉴了 mattpocock/skills 的工程化 agent 工作流（[agents/triage-labels.md](../agents/triage-labels.md) 中标注了来源），本质是把「AI 结对编程」升级成了「**AI 多成员工程团队**」的协作规范。
