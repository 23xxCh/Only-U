## 二、主要偏差：测试先行未兑现

文档明确规定「先写失败测试，再写最小实现」，但提交顺序显示的是**实现先行、测试后补**：

- feat/2：`feat: cap…` → `fix: make… cancellable` → `test: cover diagnose fallback output`（测试在实现之后）
- feat/1：`feat: launch…` → `test: cover…` → `fix: add offline preflight`（测试居中，之后还有 fix）
- feat/6：feat 提交内同时改实现和测试（test-alongside，最接近）

这是**测试后行/伴随式（test-after / test-alongside）**，不是 TDD。好的一面：测试确实存在、在合并前通过、且覆盖了关键边界（扫描上限、误报抑制、安全流程）；但测试未能驱动设计，其「防止过度设计」的收益没有拿到。

## 三、新代码的工程质量观察（portable/diagnose.ps1）

**做得好的：**

1. **逐数据源降级**：磁盘、内存、事件日志、SMART、打印机、PnP 各小节独立 try/catch，读取失败输出「无法读取…」而不是整个脚本崩溃——符合离线诊断脚本「任何机器都能跑」的定位。
2. **资源上限是硬约束**：目录扫描用可取消的 `Start-Job` 后台作业，8 秒超时 + 20,000 文件上限，跳过 reparse point（防符号链接环）、拒绝 UNC 根路径。这是对真实故障场景（TEMP 巨大/网络盘）的正确防御。
3. **误报抑制有领域判断**：事件 2004 只认 `Resource-Exhaustion-Detector` 来源；129/153/157 只认 Disk/存储驱动来源，129 还要过 provider 白名单正则（`storahci|stornvme|iaStor.*|Disk`）。测试明确断言「不把 Hyper-V/网络事件报成存储故障」——把领域经验固化成了可回归的规则。
4. **边界精度修复**（22cc457）：红灯/预警判定改用未四舍五入的 `FreePctRaw`/`CommittedPercentRaw`，显示时才取一位小数——修掉了「4.96% 四舍五入成 5.0% 逃过 <5 红灯」这类边界漏报。这是真实的 review/自审迭代在提交历史里可见。
5. **安全不变量保持**：只读诊断；清理仍预览优先；候选目录只有白名单临时目录；skill 层强制「确认/执行」二段式（[../../.dsh/skills/only-u-ops/SKILL.md](../../.dsh/skills/only-u-ops/SKILL.md)），并有测试锁定该流程。
6. **红灯区聚合**：red flags 先收集、报告置顶展示，输出结构对人（评委演示）友好。

**值得商榷的：**

1. **两个测试是「源码 grep」型**（断言脚本文本里含 `FreePctRaw`、`Start-Job`、`ReparsePoint` 等字符串）。它们锁的是实现细节而非行为，重构即红；对黑客松是廉价的回归网，长期维护是债。
2. **测试依赖宿主环境**：多个用例直接跑真实脚本、断言真实输出（如「未发现关键事件」），换一台机器可能不成立；只有 TEMP 被重定向到 `$TestDrive`。测试的可移植性弱。
3. **文档与代码的小出入**：[../发给队友2-Issue6-诊断关键指标.md](../发给队友2-Issue6-诊断关键指标.md) 写「TOP5 进程按 Commit Size 排序」，代码实际按 `PagedMemorySize64` 排序（输出标注 commit）——语义接近但严格讲不一致。
4. 扫描上限测试靠**创建 20,001 个文件 + 断言 60 秒内跑完**，是好的性能护栏，但该用例在慢盘上可能抖动。

## 四、模型演化评价

- **交付节奏健康**：每张票「feat → fix → test/docs」的小步提交 + 验证记录，形成可审计的增量；PR #5 的合并方式（GitHub merge commit）与文档约定不冲突。
- **文档进化成了活的状态页**：任务文档从「开工提示词」扩展出「当前状态 / 已交付 / 验证与边界 / 未改动」——**把验证报告和范围纪律写进了交接物**，这是本轮最值得肯定的过程改进。
- **依赖管理靠排序而非工具**：feat/6 依赖 feat/2 的合并结果，靠「先合 #2 再切 #6」解决，没有引入 rebase 复杂度，符合一天半时间盒的取舍。

## 五、综合结论

开发模式本身**没有变化**——仍是「规范驱动 + ADR 治理 + Issue 分诊 + 多 agent 并行实现」；本轮的变化是**模型经受住了执行检验**：

1. 流程约定与实现证据高度吻合（分支、提交、PR、文档交接全部兑现）；
2. 唯一实质偏差是 **TDD 顺序**（实现先行、测试后补），且测试质量参差（两个源码 grep 用例 + 宿主环境耦合）；
3. 工程判断（资源上限、误报抑制、边界精度、安全不变量）体现了超出「demo 代码」的成熟度，说明「队长定架构 + agent 按规格实现 + 人把关验收」的分工在产生真实质量。

**下一步观察点**：feat/1 与 feat/6 的 PR 是否同样走 review → 合并；Pester 是否纳入合并门禁（目前只是文档记录，未见 CI 配置）；以及演示前是否有人对 TDD 顺序和脆弱的静态测试做取舍决策。
